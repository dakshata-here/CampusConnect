# CampusConnect Database (Updated)

This version uses MongoDB Atlas through `MONGODB_URI`, so it does not depend on a MongoDB service running on one developer's machine.

## Models

User, Department, Club, ClubMembership, Venue, Event, Approval, EventRegistration, Certificate, EventFeedback, Reminder, UserRegistrationRequest, AcademicEvent, SystemSettings, AppNotification, ClubLeadTask, ClubLeadMessage, EventBroadcastEmail, EventHistory.

## Important decisions

- User types: STUDENT, FACULTY, ADMIN.
- Club Lead is a membership role, not a separate global user type.
- A club can have multiple Leads; all Leads have the same Club Lead permissions.
- There is no President or Subhead role.
- Leads are automatically club members with membership role LEAD.
- Faculty Club Lead is also the club's faculty coordinator; there is no separate coordinator field.
- CampusConnect manages its own registrations.
- Optional external registration URL/QR fields are kept separately.
- Attendance status is REGISTERED, ATTENDED, or NOT_ATTENDED.
- Registration count is calculated from EventRegistration; it is not stored on Event.
- Admin approves/rejects/requests changes/overrides but does not directly edit a proposal.
- Rescheduling keeps history.
- Certificates are generated by CampusConnect; the generated certificate file URL/path is stored.
- Academic settings are global college configuration.

## Setup

1. Copy `.env.example` to `.env`.
2. Put the MongoDB Atlas connection string in `MONGODB_URI`.
3. Run `npm install`.
4. Run `npm run seed` when seed data is desired.

Never commit `.env` or a real MongoDB password.

## Venue conflict detection

The schema stores venue/date/time and indexes those fields. The backend must still perform the actual interval-overlap check before an event is approved or scheduled.
